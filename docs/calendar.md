# Race calendar

How the public calendar (`/calendar/`) is built, refreshed and protected. The rules that must not be broken are summed up in CLAUDE.md; this is the detail.

- Static like the rest of the site, plus one Pages Function (the relay below; free plan only, no Workers Paid plan: Willi, 2026-10-07, so no Durable Objects and no rate-limit binding). Built from the catalog at every deploy, and every morning by the systemd timer `racenode-site-rebuild` on wblt-server (06:45 Paris time; by hand: `sudo systemctl start racenode-site-rebuild.service`, log: `journalctl -u racenode-site-rebuild`): that is what Google indexes.
- Source and data (`catalogSource` in `src/lib/calendar/contract.mjs`): the motorsport-data API only (`https://api.wblt-engineering.com/motorsport/v1`, WBLT-Engineering/motorsport-data), with `MOTORSPORT_DATA_API_KEY` (Cloudflare Pages env, production and preview, encrypted; Infisical racenode `prod/main` `MOTORSPORT_DATA_API_KEY_SITE`), read by the build and the relay. The app's old catalog views are gone (2026-10-14): without the key the build fails. Server-side only: the key travels in an `Authorization` header and never reaches a page (Willi, 2026-10-11: the pages stay public, bulk downloads must not be one request away). The contract keeps its fields only, the API's nested fields flattened to its columns; removed rounds never reach a page. Build side: `src/lib/calendar/build.mjs`; a failing read fails the build, so the last good deploy stays online.
- The relay (`functions/calendar/api/catalog.js` → `src/lib/calendar/relay.mjs`, `GET /calendar/api/catalog?series=<slug>`): the only door to the catalog for a browser. It answers one championship (~3 KB; the contract's fields, nothing else); without `series` it answers 400, never the whole catalog (Willi, 2026-10-18: minimal protection against scraping). From the edge cache for 5 minutes, to same-origin browser requests only (`Sec-Fetch-Site`), within a budget of 30 requests per IP and minute (kept in the isolate's memory: it stops a burst from one address, not a crawler spread over many). No PostgREST filter, column or ordering of the caller's choosing goes through; a database error says nothing about the database. One request per page view, against the free plan's 100,000 a day.
- In the visitor's browser (`src/components/calendar/LiveRefresh.astro`, `src/lib/calendar/refresh.mjs`): only a championship page asks the relay again (its championship, `?series=`) and replaces what changed since the build. The part it may replace carries `data-calendar-live` and the hash of its build render; the browser renders with the same pure function (`src/lib/calendar/render.mjs`: no clock, country names shipped by the build) and touches the page only if its hash differs. No JavaScript, or the relay or the API down: the morning's version stays, nothing visible. The index and the circuit pages (several championships) do not refresh: they keep the 06:45 build. Same weekends and related championships wait for the next build.
- `public/robots.txt` (Willi, 2026-10-18): AI training crawlers are disallowed (GPTBot, ClaudeBot, anthropic-ai, Google-Extended, CCBot, Bytespider, meta-externalagent, Applebot-Extended, cohere-ai); search engines and the assistants' search and user agents (OAI-SearchBot, ChatGPT-User, PerplexityBot, Perplexity-User, Claude-SearchBot, Claude-User) stay allowed. Names checked on the publishers' pages 2026-10-18.
- The index lists rounds not over on the build's day (`ctx.today`), every season mixed by month; rounds already run stay on the championship and circuit pages. Within a month, one section per meeting (Willi, 2026-10-18: a circuit and what races there the same weekend, the catalog's `meeting_id` on each event, `meetingsOf` in model.mjs; an event without one is a section of its own): the heading gives the circuit by its official name, `venue_name` (Willi, 2026-10-18: "Autódromo Internacional do Algarve", not "Portimão"; never the event's name), its logo, the meeting's dates (first start, last end of its upcoming rounds) and country, linked to the circuit's page when it has one; the rows below give the championship and round, their own dates only when they differ from the meeting's. Filters: discipline, region, circuit, month; they hide rows, and a meeting or month with no row left. Championship pages: "On the same weekends" = the championships sharing a `meeting_id` with one of its rounds.
- Circuit pages: a venue with 3+ race or test rounds in the catalog (rounds, not events: a double-header folded into one event counts its `round_numbers`) (`CIRCUIT_PAGE_MIN_ROUNDS`, model.mjs); its URL comes from the venue's name (`circuit-de-la-sarthe`), never from the catalog's `venue_slug` (it carries references such as `le-mans-fr-q174090` that may be cleaned up), with the country only when two venues share a name. Renaming a venue in the catalog moves its URL. The build ships the circuit pages (`venue_slug` → URL slug) in `ctx.circuitPages` (a championship page only reads its own rounds in the browser). `circuits` is reserved: a series with that slug fails the build.
- `render.mjs` is the only place the refreshable parts are written: change their markup there, never in the `.astro` pages. The index rows' classes live in `src/styles/global.css` (`.calendar-row`), not in each of the ~800 rows.
- Sample data (`src/data/calendar/sample.json`, a real extract) only where `CALENDAR_SAMPLE=1` (preview env, never production) and the API key is missing or the API does not answer: pages then say "sample data" and are noindex, and the browser re-reads a static copy of the relay's answer (`/calendar/sample-api/catalog.json`) through the same code (championship pages only).
- Tests: `npm run test:calendar` (contract, model, render, the browser refresh against the sample served as the relay, the relay's refusals, budget and cache, no key in a page).
- Logos (Willi, 2026-10-08, on condition that 80% of the championships have one; 114 of 126 on 2026-10-12): the championships' official logos, hosted by us, never linked directly. The build reads `logo_url` / `logo_light_url` / `logo_dark_url` from the API's series (`fetchCatalog(..., { logos: true })`: the relay does not ask, so the browser never sees them), `src/lib/calendar/logos.mjs` downloads each one and turns it into a small webp, and `src/pages/calendar/logos/[slug].webp.ts` serves it at `/calendar/logos/<slug>.webp`. The light variant is shown on paper; a logo made for a dark background sits on an ink chip. A logo missing or failing to download: the row stays text, the build goes on. `ctx.logos` (slug → tone) tells render.mjs which championships have one, so the browser's re-render finds the same markup and never builds a path from anything but the slug; `render.mjs` stays the only place that writes them (fixed 48×32 box, lazy, to keep ~800 rows from jumping). Circuits' logos (meeting headings; ~81 of ~1,100 circuits have one, so a text heading is the usual case): the same chain, from the `venue.logo` the API gives on each event to the build's key (`venue_logo_*`, never in the relay), served at `/calendar/logos/circuits/<slug>.webp` where the slug is the circuit's own (as its page's URL, never `venue_slug`); `ctx.circuitLogos` (`venue_slug` → { slug, tone }). Guardrail: `node scripts/guardrails.mjs --dist` (run by `npm run build` after `astro build`) fails if anything in `dist/` mentions `supabase.co`.
- Rules (Willi, 2026-10-07): dates and venues only; no organizer document, link to the official page; never team data, raw scrapes or logs. A season not published yet says so and shows the last one known.
